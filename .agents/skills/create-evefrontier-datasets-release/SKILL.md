# Create EVE Frontier datasets release

Produce a fresh snapshot with the current Go extractor and publish it to **Scetrov/evefrontier_datasets**. This skill is an operational workflow, not permission to invent release details, publish proprietary content without authorization, overwrite existing releases, or change the extractor. Follow all applicable repository and user instructions.

## Boundaries

- Do not run client executables, DLLs, compiled Python loaders, or unpickle client files. Use the extractor's confined, read-only client access. Do not modify the game installation.
- Export only the extractor's published type catalog and associated icons, not spatial data, ecosystem/dungeon definitions, fitted ship statistics, or `ship_data.csv`.
- Published is a client flag, **not** a guarantee of current availability. Type values are base client data, not effective fitted statistics. Missing icons and descriptions are not necessarily failures; report them.
- Game data and artwork may be subject to CCP terms. Do not infer redistribution rights from existing releases, the target repository's license, or this skill. Before publishing, have the operator confirm they have assessed and accept the relevant redistribution rights for both data and artwork. If they cannot, stop before remote mutation.
- Never overwrite, delete, edit, or clobber an existing release, tag, or asset. Do not push commits or modify either repository as part of this workflow unless separately requested.

## 1. Establish inputs and preflight

1. Locate the extractor checkout containing `go.mod` and `README.md`; read its instructions and current output format. Preserve existing work. Record `git rev-parse HEAD`, branch, and `git status --short`. A dirty checkout cannot be identified solely by its commit: show the operator the changed/untracked paths and ask whether to build from that exact working tree. Record a digest of the relevant source diff or otherwise identify the uncommitted source used; do not include unrelated files in the release. Prefer a clean, known commit.
2. Require only the era and cycle as release metadata inputs, for example **Era 6, Cycle 7**. Derive the tag as `e<era>c<cycle>v<revision>` and title as `Era <era>, Cycle <cycle> (v<revision>)`. Start revision at 1 for a new cycle; if matching tags or releases already exist, choose the next revision above the highest existing revision across both (inspect all pages). Do not ask the operator for a tag, title, revision, or client build. Era/cycle labels do not establish a client build. Use the Stillness installation at `C:\CCP\EVE Frontier` if present, or an installation path already supplied by the operator; ask only if the installation cannot be located unambiguously. Allocate a **new**, non-existing output path under a temporary directory outside the game directory with an existing parent; do not ask the operator to choose it.
3. Default to a published release marked latest unless the operator requests otherwise; include these settings in the final approval plan rather than asking separate setup questions. Resolve `Scetrov/evefrontier_datasets`'s default branch and its current HEAD automatically using GitHub. Use that commit as the tag target; do not ask for a target SHA. Dataset releases are asset snapshots, not releases of repository source changes, so multiple release tags may point to the same HEAD. Record the resolved SHA for reproducibility and use that exact commit throughout publication. This is the target repository commit, **not** the extractor commit or this checkout's HEAD.
4. Verify the target repository and authenticated GitHub identity with `gh auth status` and read-only `gh api`/`gh repo view` calls. Check access without displaying credentials. Check both the release and the remote tag for the derived tag. Distinguish a genuine 404/not-found from authentication, rate-limit, or network errors; stop on uncertainty. If either exists during preflight, derive the next unused revision rather than asking for a different tag. Validate the tag using `git check-ref-format refs/tags/<tag>` and ensure the automatically resolved target commit exists in the target repository. Do not assume the same local Git remote points to that repository.
5. Inspect the latest release metadata and asset names. Recent releases used `static_data.db` and `icons.zip`, sometimes `ship_data.csv`. The new database is intentionally **not schema-equivalent** to the older spatial database: it contains `Types`, `Groups`, and `Categories`. Disclose removed spatial, ecosystem, dungeon, and ship CSV content in release notes. If existing consumer compatibility is a requirement, stop and discuss it rather than claiming compatibility.
6. Run `go mod verify`, `go test ./...`, and `go vet ./...` from the extractor checkout. Build the current source with `go build -trimpath` to a new temporary path; do not use a pre-existing executable or overwrite a user's build. Stop on failure. If configured repository checks exist, run them too. Set `FRONTIER_GAME_TEST` and run the opt-in `TestInstalledGame` when available; report any inability to run it rather than claiming it passed.

## 2. Generate and validate

1. Run the freshly built executable with `-game` and `-out`, using the validated paths. The output path must not exist. If extraction fails, stop; do not publish a partial result. Do not silently relax parser schema fingerprints or integrity checks.
2. Confirm the new output contains `static_data.db`, `items.json`, `items.csv`, `report.json`, and `icons/`; never reuse the repository's existing `output/` as the generated snapshot. Parse the report and summarize counts, missing names/descriptions/classifications/icons, item issues, and source MD5s. Client MD5s detect corruption, not authenticity.
3. Independently open the generated SQLite database read-only, run `PRAGMA integrity_check` and require `ok`. Check that `Types`, `Groups`, and `Categories` exist; `Types` is non-empty, type IDs are unique and all rows are published; the type count, IDs, names, and base values match `items.json`; and the CSV row count and IDs match JSON. Check joins to groups/categories and report unresolved references or names. Check every available icon path is a regular file contained inside `icons/`, each missing icon is marked missing, and counts agree with the report. Stop on mismatches; do not substitute blanks for errors.
4. Create `icons.zip` from **only** the generated `icons/` files, keeping the `icons/` prefix and original bytes and extensions. Reject symlinks, absolute paths, `..` entries, duplicates, and unexpected files. Reopen the ZIP and compare each member's bytes or SHA-256 against the corresponding generated icon; require an exact member set. No game files or extractor binaries belong in the ZIP.
5. Stage the release assets in a new directory: `static_data.db`, `items.json`, `items.csv`, `report.json`, and `icons.zip`. Compute SHA-256 for each and prepare `SHA256SUMS.txt` using standard `<hex>  <filename>` lines. Verify those checksums against the staged bytes. Do not include raw game client resources or secrets.
6. Prepare truthful release notes containing: release tag/title; extractor commit and, if dirty, a clear working-tree qualification; client/version identification only if actually known; source checksums from the report; row/icon/missing counts; asset descriptions; checksums or a reference to `SHA256SUMS.txt`; and the limitations and historical compatibility break above. Do not claim checksums authenticate client data or that types are obtainable. Never guess a client version.

## 3. Approve and publish

Present the operator with the target repository, authenticated account, tag, exact target commit, title, draft/published state, latest setting, rights confirmation, release notes, asset names/sizes/SHA-256s, checks performed, and any missing data or compatibility concerns. Obtain explicit approval for **this exact plan** before any tag creation, release creation, or upload. If not approved, stop with local artifacts only.

After approval:

1. Recheck the remote tag and release are absent and the target commit still exists. Create a new lightweight tag pointing to the approved commit using GitHub's create-reference API (`POST /repos/Scetrov/evefrontier_datasets/git/refs`, `refs/tags/<tag>`, approved SHA). This operation must fail if the ref already exists; never force or update it. If a race or ambiguity occurs, stop.
2. Create a **draft** release against that exact existing tag using `gh release create <tag> --repo Scetrov/evefrontier_datasets --verify-tag --draft --title <title> --notes-file <notes-file>` and attach the six staged assets in the same command or by `gh release upload` without `--clobber`. If anything fails, stop and report the tag/draft state; do not delete or replace anything automatically. Do not rerun creation against an existing tag or draft without asking the operator how to recover.
3. Read back the draft release and verify its tag, title, target tag SHA, asset names and sizes. Where GitHub exposes asset SHA-256 digests, compare them to local hashes; otherwise download the uploaded assets and hash them. Ensure there are no missing or unexpected assets. Stop on any discrepancy and leave the draft unchanged for operator review.
4. If the approved state is published, publish the verified draft using `gh release edit` with the approved latest setting; otherwise leave it as a draft. Re-read the final state and report the release URL, tag SHA, draft/published/latest state, asset checksums, validation results, and any caveats. If publishing or verification fails, report the exact remaining remote state without claiming success.

Creating a skill does not itself authorize a release. Never invoke this workflow merely because the skill was installed.
